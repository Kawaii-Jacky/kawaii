## 一、协议本质（物理基础 + 三要素）

所有通信协议，无论 HTTP、WebSocket 还是 MQTT，都建立在同一套基础之上。

**物理传输介质（最底层）**：电信号（铜线/网线）、光信号（光纤）、电磁波（WiFi/蓝牙/4G/5G/LoRa）。本质是**能量或状态的变化**来编码 0 和 1。

**比特流 + 分帧**：所有协议的共同抽象，是把连续的比特流切割成有边界的数据单元（帧/包/报文）。这解决了最根本的问题：接收方怎么知道一段数据从哪里开始、到哪里结束？

> 📌 **分帧（Framing）**：在连续比特流中划定数据单元边界的机制。与本文的关联：所有上层协议（HTTP 报文头、MQTT 固定头、RESP 长度前缀）都是分帧机制的不同实现。

**协议三要素**——任何协议本质上都是在约定这三件事：

|要素|含义|举例|
|---|---|---|
|**语法 (Syntax)**|数据的格式、结构、编码方式|HTTP Header 的 `Key: Value\r\n`|
|**语义 (Semantics)**|每个字段/命令的含义|`GET` 表示获取资源|
|**时序 (Timing)**|交互顺序、状态机|TCP 三次握手、请求-响应顺序|

**一句话总结**：所有通信协议的本质，是在不可靠的比特传输信道上，通过约定数据的格式（语法）、含义（语义）和交互顺序（时序），让两个实体能够无歧义地交换信息。

## 二、分层模型（OSI / TCP/IP）

所有协议共同遵守**关注点分离**原则，每一层只关心自己的职责，向上提供服务，向下调用服务。

|层级|代表协议|职责|
|---|---|---|
|应用层|HTTP、MQTT、CoAP、WebSocket、gRPC|业务语义|
|传输层|TCP、UDP|端到端传输（可靠 or 快速）|
|网络层|IP|寻址与路由|
|链路层|Ethernet、WiFi|相邻节点间传输|
|物理层|电/光/无线|比特传输|

**核心规律**：越靠近应用层，协议越关注「业务语义」；越靠近物理层，越关注「怎么可靠地传一个比特」。所有上层协议的差异，本质上都是在**可靠性、延迟、功耗、复杂度**之间做不同的权衡。

## 三、传输层协议对比（TCP vs UDP）

### 面向字节流 vs 面向数据报

> 📌 **面向字节流（Stream-oriented）**：数据是一条没有边界的连续河流，接收方自己划分。TCP 采用此模型。

> 📌 **面向数据报（Datagram-oriented）**：数据是独立的包裹，每个包裹有明确边界，一次 sendto 对应一次 recvfrom。UDP 采用此模型。

|维度|字节流（TCP）|数据报（UDP）|
|---|---|---|
|边界|无边界，连续流|有边界，独立包|
|粘包|存在，需应用层处理|不存在|
|顺序|严格保序|可能乱序|
|可靠性|可靠，丢了重传|不可靠，丢了就丢|
|传输效率|内核可合并优化|一发一收，开销固定|
|适用场景|HTTP、文件传输、数据库|DNS、视频通话、游戏|

**最关键差异**：TCP 内核可以自由拆包/合包，边界完全消失，应用层必须自己处理；UDP 天然保留边界，但可靠性需应用层自理。

### TCP 粘包问题与解决方案

TCP 不保留任何发送边界，内核可随意拆包、合包，导致「粘包」问题。解决方案：

- **固定长度**：每条消息固定 N 字节

- **分隔符**：用特殊字符（如 `\n`）标记边界

- **长度前缀**：报文头携带消息体长度（HTTP、gRPC、MQTT 均采用此方式）

### TCP 核心优势

TCP 的所有优势都围绕一个目标：**在不可靠的网络上，提供可靠的字节流传输**。

**1. 可靠传输（ACK + 超时重传）**：发送方每发一个包，接收方回 ACK 确认；超时未收到 ACK 则重传。应用层完全感知不到丢包的存在。

**2. 有序传输**：IP 层不保证顺序，TCP 用序列号（Sequence Number）重排，应用层永远看到有序数据。

**3. 流量控制（滑动窗口）**：接收方在 ACK 中告知剩余缓冲区大小，发送方动态调整速率，防止接收方被压垮。

**4. 拥塞控制**：慢启动探测网络容量，检测到拥塞（丢包）立即降速，保护整个网络生态。

**5. 错误检测（校验和）**：每个报文携带校验和，损坏的数据直接丢弃等待重传。

**优势的代价**：额外 ACK 包、重传延迟、三次握手建立延迟（1.5 RTT）、主动降速、队头阻塞——这正是视频通话/游戏选择 UDP 的原因。

### TCP 四次挥手

> 📌 **四次挥手（Four-way Handshake）**：TCP 关闭连接的标准流程，确保双方数据都完整发送后再断开。与本文关联：理解挥手触发时机是理解 TCP 连接生命周期的关键。

**触发本质**：挥手不是 TCP 自动发起的，而是**应用程序调用** `**close()**` **或** `**shutdown()**` 时，TCP 内核才发送 FIN 包。

**常见触发场景**：

|场景|说明|
|---|---|
|业务完成|HTTP/1.0 响应发完后 Server 主动关闭|
|用户主动断开|关闭 Tab、Ctrl+C、退出登录|
|服务端踢客户端|超时、限流、非法请求、服务重启|
|Keep-Alive 超时|HTTP 长连接空闲超时后关闭|
|进程退出|OS 自动对所有 socket 发 FIN|

**TIME_WAIT 等待 2MSL 的原因**：防止最后一个 ACK 丢失导致对方重发 FIN 时无人回应；防止旧连接的「幽灵包」干扰新连接。

**特殊情况 RST**：不走四次挥手，直接强制重置。触发场景包括：端口无进程监听、防火墙强制中断、`SO_LINGER=0` 时调用 `close()`。

### 心跳包

> 📌 **心跳包（Heartbeat）**：一种应用层设计模式，定时发空包检测「假连接」，不属于任何特定协议。与本文关联：是 TCP 长连接保活机制的补充手段。

心跳包解决的问题：网络中断或 NAT 超时后，连接处于「假连接」状态，双方都以为连接还在，但数据永远发不出去。

|层面|机制|默认间隔|
|---|---|---|
|TCP Keepalive|系统内置，默认关闭|2 小时|
|WebSocket|PING/PONG 帧，协议内置|应用自定义|
|MQTT|PINGREQ/PINGRESP，协议内置|连接时协商|
|HTTP/2|PING 帧，协议内置|应用自定义|
|自定义 TCP|完全自己实现|自己定义|

**两个作用**：检测死连接 + 防止 NAT 超时清理连接映射表。

## 四、应用层协议全景

### HTTP / HTTPS

> 📌 **HTTP（HyperText Transfer Protocol）**：基于 TCP 的无状态请求-响应协议。HTTPS = HTTP + TLS 加密层。与本文关联：最典型的应用层协议，是理解其他协议的参照基准。

|版本|关键改进|
|---|---|
|HTTP/1.0|每次请求新建连接|
|HTTP/1.1|Keep-Alive 复用连接|
|HTTP/2|多路复用、头部压缩、服务端推送|
|HTTP/3|基于 UDP+QUIC，解决 TCP 队头阻塞|

**HTTP/3 为何改用 UDP**：HTTP/2 虽支持多路复用，但底层 TCP 一丢包，所有请求的处理全部阻塞（队头阻塞）。QUIC 在 UDP 上自己实现可靠传输，每个流独立，一个流丢包不影响其他流。

### WebSocket 与 SSE

> 📌 **WebSocket**：基于 TCP 的全双工协议，通过 HTTP 握手升级建立持久连接。帧头仅 2-14 字节，开销极小。

> 📌 **SSE（Server-Sent Events）**：基于普通 HTTP 的服务端单向推送，自动重连，ChatGPT 流式输出即采用此协议。

### 物联网协议

|协议|传输层|模式|最小报头|核心场景|
|---|---|---|---|---|
|MQTT|TCP|发布-订阅|2 字节|智能家居、车联网、工业传感器|
|CoAP|UDP|请求-响应（类 HTTP）|4 字节|极低功耗设备、NB-IoT、智能电表|
|AMQP|TCP|消息队列|较大|金融系统、电商订单、微服务异步通信|

**MQTT QoS 等级**：QoS 0（最多一次，可能丢）、QoS 1（至少一次，可能重复）、QoS 2（恰好一次，最可靠）。

### 远程调用协议

|维度|REST (HTTP+JSON)|gRPC (HTTP/2+Protobuf)|
|---|---|---|
|格式|文本，可读性好|二进制，不可直接读|
|性能|JSON 解析较慢|Protobuf 序列化快 5-10x|
|契约|无严格契约|强类型 .proto 文件定义|
|流式|单向请求响应|支持双向流式传输|
|适用|公开 API、前后端通信|微服务内部通信、高性能场景|

> 📌 **WebRTC（Web Real-Time Communication）**：P2P 直连协议，基于 UDP，内置 DTLS 加密，通过 ICE/STUN/TURN 解决 NAT 穿透。用于视频会议（Zoom、Meet）、P2P 文件传输。

## 五、通信模式全景

|模式|方向|实时性|代表协议/技术|
|---|---|---|---|
|请求-响应|客户端主动|同步|HTTP、gRPC unary|
|发布-订阅|解耦广播|异步|MQTT、Kafka、Redis Pub/Sub|
|推送|服务端主动|强实时|WebSocket、SSE、APNs|
|拉取/轮询|客户端主动|弱实时|Polling、长轮询|
|流式|单/双向持续|强实时|gRPC Stream、WebSocket|
|点对点 (P2P)|双向直连|最低延迟|WebRTC、BitTorrent|
|管道|批量请求不等响应|高吞吐|Redis Pipeline、HTTP/1.1 Pipeline|
|消息队列|单消费者|异步|RabbitMQ、RocketMQ|

**发布-订阅 vs 消息队列的关键差异**：发布订阅中一条消息所有订阅者都收到（广播）；消息队列中一条消息只有一个消费者收到（竞争消费）。

**模式选择决策树**：

- 需要一问一答 → 请求-响应

- 需要广播给多人 → 发布-订阅

- 服务端实时通知客户端 → 推送（WebSocket/SSE）

- 客户端定时取数据 → 拉取/轮询

- 传输大文件或 AI 输出 → 流式

- 视频通话/P2P → WebRTC

- 任务异步处理、削峰填谷 → 消息队列

## 六、Redis：通信协议知识的具体实现集合

Redis 不是本地库，而是一个独立进程，客户端通过网络与之通信，建立在 TCP 之上，自定义了 RESP 作为应用层协议。

> 📌 **RESP（Redis Serialization Protocol）**：Redis 自定义的极简文本协议，用长度前缀解决粘包问题。与本文关联：是「长度前缀分帧」方案的典型实现。

**RESP 报文示例**（`SET name alice`）：

```jsx
*3\r\n     ← 3个参数
$3\r\n     ← 第1参数长度
SET\r\n
$4\r\n
name\r\n
$5\r\n
alice\r\n
```

**Redis 与通信模式的对应关系**：

|Redis 特性|对应通信模式|
|---|---|
|Pipeline|管道模式：连续发命令不等响应，批量收结果|
|Pub/Sub|发布-订阅模式：SUBSCRIBE 建立长连接，PUBLISH 广播|
|主从复制|推送模式：Master 有数据变更推送给 Slave|
|BRPOP|长轮询模式：没有消息则阻塞等待|

**Redis 常见使用场景**：缓存（最核心）、分布式锁（SETNX 原子操作）、限流（INCR + EXPIRE）、排行榜（Sorted Set）、轻量消息队列（List + BRPOP）。

**缓存三大问题**：

|问题|触发条件|解决方案|
|---|---|---|
|缓存穿透|查询不存在的数据，每次打到数据库|布隆过滤器 / 缓存空值|
|缓存击穿|热点 key 突然过期，瞬间大量请求打数据库|互斥锁重建 / 热点 key 永不过期|
|缓存雪崩|大量 key 同时过期，数据库瞬间压力暴增|过期时间加随机值 / 多级缓存|

> 🔗 **横向关联**：Redis Pipeline 与 HTTP/1.1 Pipeline 形成**镜像关系**——两者都是「管道模式」的应用，核心思路相同：批量发送请求不等响应，用吞吐量换取延迟优化。Redis Pipeline 减少的是 Redis 命令的 RTT，HTTP Pipeline 减少的是 HTTP 请求的 RTT。
