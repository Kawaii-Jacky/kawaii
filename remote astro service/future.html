01 — Migration goal

为什么要自己搭平台

Blynk 已经完成了样机阶段的远程控制和遥测验证。后续设备数量、数据类型和控制流程会继续增加，自建平台便于管理通信协议、历史数据、账号权限和客户端功能。

01

数据自己管理

环境、能源、设备状态、报警和操作记录写入自己的数据库，保留时间和备份策略由项目需要决定。

02

接口统一

三个 ESP32 使用统一的 MQTT Topic、消息格式和设备身份，管理后台与响应式客户端共用同一套后端接口。

03

功能方便扩展

以后新增传感器、观测站或自动化流程时，可以直接扩充设备模型和页面，不受现成控件限制。

02 — Target architecture

计划中的平台结构

设备负责采集、执行和本地保护。云端处理消息、存储、通知与媒体接入；管理后台和统一客户端从同一后端读取数据并发送指令。

03 — Work sequence

按这个顺序实施

先跑通设备到数据库的最小链路，再做管理功能和客户端。每一步都保留测试与回退方案。

  1. PHASE 01 / SERVER

    申请并配置云服务器

    配置域名、HTTPS、TLS 证书、防火墙、日志、自动备份和服务监控，建立开发与生产环境。

  2. PHASE 02 / MQTT

    部署 MQTT Broker

    定义 Topic、QoS、保留消息、遗嘱消息和设备身份。每台设备使用独立凭据，控制指令需要权限校验。

  3. PHASE 03 / DATA & MEDIA

    接入后端、数据库和媒体服务

    保存遥测、设备状态、操作记录和报警事件，维护设备上线与下线；接入邮件和短信任务，并管理 RTSP 地址、端口和视频转发权限。

  4. PHASE 04 / CLIENTS

    开发管理后台和统一客户端

    管理后台处理数据、设备与投送配置；网页端和移动端采用同一套功能，根据桌面与手机屏幕调整布局。

  5. PHASE 05 / PCB & DEHUMIDIFICATION

    整合硬件与加入除湿控制

    把分散的主控、采样、驱动和通信接口整合到专用 PCB，并预留除湿执行器接口；根据舱内湿度阈值、滞回区间和最长运行时间控制除湿。

  6. PHASE 06 / CUTOVER

    逐台设备切换

    新旧通道先并行测试，核对数据、指令和离线恢复。连续运行稳定后停止 Blynk 服务，保留配置与历史记录备份。

04 — Cloud & hardware

云端和硬件一起推进

软件平台负责数据、通知和远程操作，专用电路板与除湿功能提高现场系统的集成度和环境适应能力。

Admin & Data / 管理后台

数据、设备与信息投送

数据库保存历史遥测和操作记录；后台维护设备上线与下线，配置邮件和短信投送任务，并管理 RTSP 地址、端口及访问权限。视频流由独立媒体服务转发。

  • History Data
  • Device Presence
  • Email & SMS
  • RTSP Gateway
Responsive Client / 统一客户端

网页端与移动端功能一致

桌面和手机共用状态查看、历史曲线、远程控制、报警处理和视频监控功能，只根据屏幕尺寸调整导航、卡片和操作区布局。

  • Responsive UI
  • Realtime Charts
  • Remote Control
  • Video View
Dedicated PCB / 专用电路板

整合分散的控制功能

把当前分散在洞洞板和模块上的主控、传感器、功率采样、驱动和通信接口整理成原理图并绘制专用 PCB，减少跳线和接插件数量，同时保留检修与扩展接口。

  • Schematic
  • PCB Layout
  • Power & Signal
  • Service Ports
Humidity Control / 除湿

关顶后自动控制舱内湿度

增加舱内湿度检测和除湿执行器接口，按阈值与滞回区间自动启停，并设置最长运行时间、故障告警和远程手动控制。具体除湿方式会根据舱内容积与实测效率选择。

  • Humidity Sensor
  • Hysteresis
  • Runtime Limit
  • Fault Alert
Safety baseline

断网时，现场仍能安全收尾

关顶、雨水保护、电池保护、限位判断和基础除湿继续由本地控制器执行。云端负责远程操作、数据记录和通知，不接管必须即时完成的安全动作。

退出 Blynk 的条件：关键功能完整、权限与备份可用、断线重连稳定，并完成一段时间的新旧平台并行测试。
